# WatchKit — agent notes

- The coalescing table in the header and `merge_one` in `src/lib.rs` are the product contract, not an implementation detail: created+deleted = no event at all (net-zero), deleted+created = one modified, renamed+deleted = deleted of the ORIGINAL path, created+renamed = created at the new name. Any change to a row needs the matching test changed in the same commit and a header update — consumers plan around these merges.
- Loss must stay counted, never silent: overflow drops the OLDEST pending events and increments `dropped`, which both `wa_poll_events` and `wa_status` report. Do not add a path that discards an event without either merging it (coalesced_count rises) or counting it (dropped rises, or an acknowledged discard via since_seq). Net-zero removal is a merge, not a drop — it must not touch `dropped`.
- Cache invalidation is event-driven at SCAN time (`do_scan` invalidates before merging), not at poll time: a consumer that never polls still gets fresh folder sizes. Weakening that to poll-time invalidation reintroduces stale reads for exactly the consumers the coordinator exists for.
- The cache race guard is the epoch: a folder/search walk that overlapped any event-producing scan returns its result UNCACHED rather than storing a possibly-stale entry. Do not "optimize" it into always inserting.
- Directories never emit `modified` (their mtime moves with every child change) and roots themselves are never snapshot entries. Adding either back doubles event volume with pure noise and breaks the deterministic event-count tests by design.
- Polling is the v0.1 backend by design: deterministic, portable, driven synchronously by `wa_scan_once` in tests (tests use `poll_interval_ms: 0`; the one background-thread test waits on an outcome with a deadline, never a fixed sleep). A native backend belongs behind the same queue/cache contracts per ROADMAP — never as a second, divergent event path.
- Rename pairing is a documented size+mtime heuristic (files only, greedy, sorted). It must stay documented as a heuristic in the header and README — presenting it as exact rename tracking would be a false claim.
- `wa_close` signals and JOINS the polling thread. A close that detaches "for responsiveness" silently breaks the orphan-thread guarantee. Scans are serialized on `scan_lock` so background and manual scans never apply snapshots out of order — keep that lock around the whole walk+diff+merge.
- The JSON engine (src/json.rs) is the family design — duplicate keys in one object are a PARSE ERROR by design; do not "fix" that into last-wins.
- Zero dependencies; the engine core is pure `std::fs` (polling is the portable core). Since v0.2 there IS a `src/platform.rs` — the ReadDirectoryChangesW backend that ROADMAP item 1 authorized. Its rules: the parser and the snapshot-merge stay pure and platform-free; the Windows thread feeds the SAME pipeline (`apply_observed_changes` / `do_root_rescan` / the shared apply tail), never a second event path; a backend that cannot start — or dies — falls back to polling AND reports polling (`wa_status` `"backend"` is the running backend, never the requested one); overflow and malformed completions degrade to a per-root rescan, never to silently missed changes; manual mode (`poll_interval_ms: 0`) always reports polling, because scan_once is the driver there. The RDCW runtime is Unverified until a field test on a real Windows machine runs it.
- Gate: WinDevKit tools/gate.sh (fmt + clippy both targets + full tests). Check/clippy do not link — CI's real Windows build is the link gate.
